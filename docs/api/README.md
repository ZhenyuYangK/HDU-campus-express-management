# 接口协作规范

## 当前范围

本文件与`openapi.yaml`共同定义前后端公共协议，是项目工程约定。当前没有已确认的业务端点，OpenAPI的`paths`保持为空；Swagger UI可以查看公共Schema，但还不能联调业务。[项目计划书](../management/plans/project-plan.md)已确认学生、工作人员、管理员三类角色及业务范围，具体操作权限、路径和数据字段在需求与设计阶段登记。

OpenAPI是接口结构的唯一维护入口；本文件解释协作规则。两者发生冲突时必须一起修正，不允许前端、后端各维护一套不同定义。

## 传输与命名

| 项目 | 约定 |
| --- | --- |
| 基础路径 | `/api/v1` |
| 开发地址 | `http://localhost:8080/api/v1`，应用初始化并启动后才可访问 |
| 数据格式 | 请求和响应使用`application/json`、UTF-8 |
| 资源路径 | 小写英文复数名词，多词用短横线，资源ID放路径参数 |
| JSON字段 | camelCase |
| 主键、单号、手机号等标识 | JSON字符串，避免大整数精度与前导零丢失；具体长度在业务Schema中定义 |
| 时间 | RFC3339，必须包含`Z`或时区偏移，如`2026-10-22T10:30:00+08:00` |
| 纯日期 | `YYYY-MM-DD` |
| 必填与可空 | 分别通过`required`与`nullable`定义，不把空字符串当作缺省值 |
| 业务枚举 | 经需求评审后登记，前后端使用相同枚举值 |
| 认证 | 三类角色范围已确认，具体认证方案与操作权限待设计；确认后统一补充`securitySchemes`及每个操作的`security` |

GET读取资源，POST创建资源或执行已确认的业务动作，PUT完整替换可编辑内容，PATCH局部修改，DELETE删除。每个接口只声明实际需要的方法，不机械生成全部CRUD。

## 请求与响应

客户端可提供`X-Request-Id`，限制1～64个字母、数字、下划线或短横线；未提供时由后端生成。后端将最终值放入响应头和响应体，用于关联问题记录。此能力是待实现的技术契约。

成功响应统一为：

```json
{
  "code": "OK",
  "message": "成功",
  "data": {},
  "requestId": "req-example-001"
}
```

`data`必须是对象或`null`。每个业务接口必须将对象细化为明确Schema，禁止以通用对象代替最终字段定义。列表也放在对象中，使用`data.items`。

失败响应统一为：

```json
{
  "code": "INVALID_ARGUMENT",
  "message": "请求参数不符合约定",
  "data": null,
  "requestId": "req-example-001",
  "errors": [
    {"field": "size", "message": "取值范围为1到100"}
  ]
}
```

`errors`仅在需要逐字段说明时返回。错误响应不包含异常堆栈、数据库语句或凭据。

## 分页

- 页码参数为`page`，从1开始，默认1。
- 每页数量为`size`，默认20，范围1～100；非法值返回400，不默默改成其他值。
- 分页结果的`data`为`{items, page, size, total}`，`total`表示筛选后的总记录数，空结果使用空数组和0。
- 每个列表接口明确筛选字段及默认排序，排序必须稳定；有排序参数时列出允许字段和方向，不直接透传数据库列名。
- 非分页集合须在接口说明中明确，不自动套用分页参数。

## HTTP状态与错误码

| HTTP状态 | code | 使用场景 |
| --- | --- | --- |
| 200 | `OK` | 查询、修改、删除等同步操作成功 |
| 201 | `OK` | 创建成功；适用时返回`Location` |
| 202 | `OK` | 接受了契约明确的异步任务，不代表完成 |
| 400 | `INVALID_ARGUMENT` | 缺少参数、格式错误或字段校验失败 |
| 401 | `UNAUTHENTICATED` | 认证方案确定后用于未认证或认证失效 |
| 403 | `FORBIDDEN` | 认证方案确定后用于无权限 |
| 404 | `NOT_FOUND` | 目标资源不存在 |
| 409 | `CONFLICT` | 与资源当前状态或唯一约束冲突 |
| 500 | `INTERNAL_ERROR` | 未预期的服务异常 |

本项目成功操作保留响应体，因此不使用204。失败使用相应HTTP状态，不能全部返回200再让前端猜测。

业务错误码须在接口登记后扩展，采用大写英文加下划线，并说明触发条件。重复提交、并发修改、状态迁移及唯一性规则在相应业务需求确定后定义，当前不擅自规定。

## 接口登记与评审

每个端点必须包含：需求编号、方法与路径、唯一`operationId`、输入Schema、成功及失败响应、权限、业务约束、正反例和验收用例。新增公共字段、枚举及错误码同时更新相关Schema。

| 需求编号 | 方法与路径 | 权限 | 前端负责人 | 后端负责人 | 测试负责人 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| 待需求分析 | 尚未登记业务端点 | 待确认 | 待登记 | 待登记 | 待登记 | 待确认 |

接口从“草案”经前后端和测试共同评审进入“已确认”，实现后进入“已实现”，按契约验证通过才进入“已联调”。变更时写明兼容性和调用方影响，更新本表、OpenAPI及相关用例。

OpenAPI3.0.3格式依据[官方规范](https://spec.openapis.org/oas/v3.0.3)。公共类型已经定义，不代表应用已实现这些能力。
