# 校园快递收发系统项目计划书

## 项目概况

本项目为杭州电子科技大学软件工程课程设计项目，建设单驿站双端校园快递收发系统。学生端支持个人查询、取件相关操作和寄件申请；工作人员端承担驿站收发处理，同时提供管理员使用的账号、权限及基础信息管理功能。系统采用Spring Boot+Vue3+MySQL，使用Docker在演示电脑本地运行，通过不同账号展示三类角色的操作。

计划周期为第5～15教学周，共11周，暂不填写日历日期。团队由项目负责人和成员A、B、C、D共5人组成，均参与开发，采用业务模块分工。每人每周计划投入10～12小时，包含开发、会议、评审、测试和文档；总计划投入550～660人时。成员代号用于任务分配，正式课程材料按真实姓名和学号登记。

第6周确认需求与原型，第7周确认总体设计、数据库设计和接口首版，第8周跑通首条完整业务流程，第11周完成全部计划功能，第12～13周开展集中测试与修复，第14周完成材料核对和演练，第15周完成课程验收。

当前仓库具备工程目录、协作规范、公共接口约定和Docker配置，前后端业务目录仍为占位结构。本计划安排后续需求、设计、开发和验收工作；任务实际进展在[团队分工与任务登记](../team.md)维护。

## 项目目标与范围

### 角色和使用范围

| 角色 | 业务范围 | 权限验收重点 |
| --- | --- | --- |
| 学生 | 办理个人查询、取件相关操作和寄件申请 | 只能访问本人获准查看和办理的业务 |
| 工作人员 | 执行驿站收件、取件核验、寄件受理及异常处理 | 只能执行授权的驿站业务操作 |
| 管理员 | 额外管理账号、权限和必要的基础信息 | 管理操作与普通业务操作的权限边界清楚 |

双端指学生端与驿站工作人员端，管理员通过授权的管理功能操作。第一版建设范围限定为单驿站、本地课程演示，开发任务以以下五组需求为依据。

### 业务范围及主责

下列REQ编号是项目计划中的初步需求分组，用于追踪后续分析、设计和用例；具体字段、状态及接口在需求和设计阶段确认。

| 需求编号 | 计划交付范围 | 开发主责 |
| --- | --- | --- |
| REQ-001 | 登录、三类角色权限、账号管理和必要的基础信息维护，公共框架及系统集成 | 项目负责人 |
| REQ-002 | 收件入库、退件处理，以及与查询、取件流程的数据衔接 | A |
| REQ-003 | 学生个人查询、工作人员核验取件、拒收相关处理，与退件流程衔接 | B，退件交接由A协同 |
| REQ-004 | 学生寄件申请、工作人员受理、登记寄出及取消寄件 | C |
| REQ-005 | 简单业务统计及相应展示，统计结果与实际业务记录保持一致 | D |

必须完成核心收发流程、拒收与退件、取消寄件和简单统计。第6周由各模块负责人明确拒收与退件的区别、操作主体、允许操作的条件、取消寄件的时点，以及统计指标和计算口径，由项目负责人组织确认。该阶段同步明确学生取件相关操作与工作人员核验的分工。

真实短信、在线支付、快递物流平台对接、多驿站协同和公网部署不列入本版计划。新增内容应经过需求变更评估，不能在原计划中直接追加。

## 组织分工与资源安排

### 人员主责

| 成员 | 开发主责 | 兼任职责及主要交付 |
| --- | --- | --- |
| 项目负责人 | 公共框架、账号权限与基础信息、系统集成 | 项目计划、任务协调、接口与数据库公共变更协调、周报汇总、版本与验收组织 |
| A | 收件与退件模块的前端、后端和数据实现 | 汇总业务流程和功能分析；完成本模块数据分析、原型、设计、用例和修复 |
| B | 学生查询与取件模块的前端、后端和数据实现 | 协调双端原型及页面交互一致性；完成本模块需求、设计、用例和修复 |
| C | 寄件与取消模块的前端、后端和数据实现 | 汇总数据分析与数据库设计材料、整理源码交付包；完成本模块原型、设计、用例和修复 |
| D | 统计模块的前端、后端和数据实现 | 系统测试统筹、用例与BUG清单汇总、课程材料核对；完成本模块需求、设计和修复 |

每名成员负责本模块的需求、前后端、数据库相关变更、测试和文档。A、B、C、D的汇总职责不替代其他成员提交本模块材料的责任。D组织系统测试，缺陷仍由所属模块负责人修复；跨模块问题由项目负责人协调。

每个PR至少由一名其他成员评审。涉及查询、取件、拒收和退件的改动由A、B相互核对；寄件与统计的改动由C、D相互核对；公共框架、权限及公共数据变更由受影响模块成员参与评审。所有公共接口和数据库迁移集中协调后修改。

### 工时预算

按每人每周10小时安排基础工作量，另有每人每周可以有2小时的弹性投入，用于返工、协作和风险处理。各阶段工时均包含当期会议、评审和周报工作。

| 阶段 | 教学周 | 团队基础投入 |
| --- | --- | --- |
| 启动、计划和需求分析 | 第5～6周 | 100人时 |
| 设计、接口、框架及首条流程 | 第7～8周 | 100人时 |
| 模块开发与滚动联调 | 第9～11周 | 150人时 |
| 集中测试、修复及复测 | 第12～13周 | 100人时 |
| 材料核对及演练 | 第14周 | 50人时 |
| 课程验收及归档 | 第15周 | 50人时 |
| 合计 | 11周 | 基础550人时，弹性投入最多110人时 |

开发和演示使用现有电脑及仓库规定的Docker工具环境。第5周检查各成员环境，第14周在实际演示电脑再次检查启动、数据库数据、角色账号及操作流程。框架开发先提供各模块所需的最小可用公共能力，避免其他成员等待完整管理页面完成后才能接入。

## 质量要求与验收安排

### 功能与权限验收

全部REQ-001～REQ-005逐项演示和检查。核心收发流程覆盖正常与异常情况，核对学生个人数据访问范围、工作人员业务权限、管理员管理权限以及保存后的数据。A、B联合核对拒收、退件和取件之间的处理衔接；C核对寄件申请、受理、寄出与取消的规则；D使用同一批业务记录核对统计结果。

阻断业务流程、造成数据错误或破坏已确认权限边界的问题，须由所属模块负责人修复并复测后交付。其他遗留问题记录影响、责任人和后续安排，由项目负责人组织判断是否影响验收。测试记录包含用例、环境、预期、实际表现、结果和证据，未执行项说明原因。

代码修改先由模块负责人验证，再经其他成员评审；公共接口或数据结构变更同步更新OpenAPI、设计与相关用例。测试使用可公开的合成数据，本地演示按学生、工作人员、管理员账号分别检查，重启应用后复查已保存业务数据。

## 执行监控与变更管理

每周组织两次20～30分钟短会，分别检查开发进展和联调问题，周末汇总周报。成员会前更新任务实际状态、交付物、验证结果及阻塞；负责人协调接口、跨模块问题和人手安排，D跟进测试问题，会议结论写入当周周报。

每项任务登记主责、需求、依赖、计划完成周、验收条件和实际证据，状态使用“待开始、进行中、待评审、待验证、完成”。进度以实际交付物及验证情况判断，不用代码行数或主观百分比代替完成条件。周报逐人说明工作，记录延期原因、集中讨论结论和下周重点。

需求调整由提出人说明原因、涉及功能及对接口、数据库、开发、测试和材料的影响，项目负责人组织受影响成员评估并确认。经确认后同步需求、OpenAPI、设计、用例、任务表和周报。第10～11周落后时，先暂停新增需求，简化页面表现、统计展示和操作细节，在保留已确认业务行为和验收标准的前提下重新分配人手，保留第12～13周测试及第14周演练时间。业务条件、权限或异常处理的删减不属于页面简化，须作为范围变更另行确认。

每个模块的前后端改动使用同一业务契约；任务分支和PR执行[团队协作规范](../../collaboration.md)。公共框架和公共数据变更由负责人协调，模块负责人维护各自实现和用例。开发问题可按需在本机保留，团队共享问题由成员在周报、PR或Issue中手动总结。
