# 团队协作规范

## 依据与生效范围

本规范适用于校园快递收发系统。课程课件规定4～5人组队、推选组长、明确分工并提交周报。以下分支、目录、接口和评审规则是本项目的工程约定，不作为教师额外要求。

## 分工与任务管理

- [团队分工表](management/team.md)统一登记成员姓名、角色代号、负责范围、评审搭档和任务。已确认项目负责人为杨振煜，A为任奕阳，B为张海睿，C为沈翔宇，D为戴靖桓；任务主责使用姓名。课件列出的多个岗位由现有5名成员兼任。
- 每项任务登记需求/任务编号、负责人、目标目录、前置依赖、验收条件和计划完成时间。
- 任务状态统一为“待开始、进行中、待评审、待验证、完成”。有阻塞时补充阻塞原因和处理人。
- 两人同时修改公共接口、构建配置、数据库迁移或公共组件前先协调；公共文件由任务负责人集中修改。
- 每周按课程模板更新进展、个人工作、集中讨论结果、延期及遗留问题、下周重点。Markdown草稿不能代替课程要求的DOCX交付。

## Git流程

主分支为`main`，保持可交付状态；从`main`建立任务分支：

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| 功能 | `feature/<task-id>-<short-name>` | `feature/task-001-api-contract` |
| 修复 | `fix/<issue-id>-<short-name>` | `fix/dev-0002-env-config` |
| 文档 | `docs/<task-id>-<short-name>` | `docs/task-002-weekly-report` |
| 环境 | `chore/<task-id>-<short-name>` | `chore/task-003-docker` |

```powershell
git switch main
git pull --ff-only origin main
git switch -c docs/task-001-requirements
```

以上命令用于远程已有`main`的正常协作阶段。仓库首次初始化尚无提交时，由组长先检查内容、创建首次提交并推送，再通知成员克隆。

提交格式为`type(scope): 中文说明`，类型使用`feat`、`fix`、`docs`、`test`、`refactor`、`chore`。一笔提交只表达一个明确目的。

推送任务分支后发起PR，至少由1名其他成员评审，完成相关验证后合并。禁止强推公共分支、提交本地密码或用整个目录覆盖别人的修改。这里规定团队操作流程，尚未在GitHub后台设置分支保护。

## 接口先行

1. 将功能整理为需求编号，确认参与角色、业务流程、输入输出和验收条件。
2. 在`docs/api/openapi.yaml`登记接口、Schema和示例，同时更新接口规范的登记表。
3. 前后端及测试负责人共同检查字段、类型、枚举、权限、错误及边界条件。
4. 通过PR确认后再分别实现。前端使用同一契约，临时模拟须标注来源，不作为后端测试证据。
5. 变更路径、字段、必填项、枚举、权限或响应结构时，列出受影响调用方、兼容方案及迁移时间，更新契约和测试后合并。

公共协议见[接口规范](api/README.md)。角色、状态及业务端点未确认前不得自行定稿。

## 目录和代码约定

- 后端使用Java21和Maven，根包为`cn.edu.hdu.express`。Controller处理HTTP及参数校验，Service承载业务规则与事务，Repository负责持久化，DTO承载接口输入输出，Entity表示持久化实体。持久化框架在初始化应用时确定，当前不混用多个方案。
- 前端使用Vue3和TypeScript。页面放`views/`，公共组件放`components/`，HTTP调用集中在`api/`，跨组件状态放`stores/`，类型放`types/`。后续初始化时固定依赖版本并提交`package-lock.json`，协作者使用`npm ci`。
- Java类使用PascalCase，方法和变量使用camelCase；Vue组件使用PascalCase文件名；JSON字段使用camelCase；数据库表和列使用snake_case。
- UTF-8、LF换行、空格缩进，遵循根目录`.editorconfig`。文档中英文与中文之间不加空格。
- 数据库变更进入`database/migrations/`，使用`V<递增编号>__<说明>.sql`命名。已合并并执行的迁移不改写，新增后续迁移；迁移工具在应用初始化时确定。
- 测试数据只使用可公开的合成数据。数据库表、业务枚举和索引必须关联已确认的数据分析或设计文档。

## 联调与测试

- 统一使用根目录Compose配置和`.env.example`声明的变量；修改端口或镜像时同步开发环境文档。
- 前端浏览器访问本机后端地址，容器内后端通过服务名`mysql`访问数据库。不能把容器内`localhost`当成其他容器。
- 每个PR填写实际测试命令、预期、实际结果及证据。未执行必须写明原因。
- 课程最终测试至少覆盖两个模块，且至少包含一个录入或编辑类型用例和一个查询类型用例，并维护BUG清单；当前不指定尚未确认的业务模块。
- 本机开发问题可按需参考[问题模板](templates/issue-template.md)在`docs/development-issues/`保留，该目录不纳入Git跟踪。需要共享的问题由组员在周报、PR或Issue中手动总结，保留相关环境和实际验证结果。

## 完成条件

需求与接口已确认；修改范围清楚；相应实现和文档一致；相关验证有真实结果；影响团队的未解决问题已说明；其他成员完成评审。没有业务代码时只验收结构、规范和环境配置，不宣称业务完成。
