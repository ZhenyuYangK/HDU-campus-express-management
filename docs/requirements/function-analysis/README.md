# 功能分析团队规范

## 依据与交付

开始前读取[团队进度](../../management/team.md)、[全过程规范](../../standards.md)、已确认需求、业务流程、[数据分析规范](../data-analysis/README.md)及对应数据分析。涉及对外调用时读取[接口规范](../../api/README.md)和[OpenAPI](../../api/openapi.yaml)。

各模块负责人按教师模板完成本模块XLSX，张海睿汇总。文件放在本目录的`姓名_REQ-编号/`，缺少的说明放同目录Markdown，保留模板布局。课程要求见[CR-03](../../course-requirements.md)。

## 功能分解与统一用语

功能项描述角色完成的业务目标，分解到能明确输入、结果和验收条件。查询、提交、撤回等不同业务动作分别说明；页面、按钮、数据库表和通用增删改查不能直接代替功能分析。

沿用REQ归属，为功能项分配`FUNC-<三位需求序号>-<两位流水号>`。同一业务动作在功能表、流程、原型和接口说明中使用统一名称；一个功能可对应多个页面或接口，不机械规定一一对应。跨模块交接引用对方功能编号，不在两份材料中各定义一套处理规则。

## 每个功能项的必需说明

| 内容 | 要求 |
| --- | --- |
| 标识与来源 | 功能编号、名称、REQ、流程及规则出处 |
| 角色与范围 | 谁可执行、可访问哪些数据，区分角色权限与资源归属 |
| 前置与触发 | 执行条件、入口、当前业务条件及所需公共能力 |
| 输入 | 引用数据项编号，说明哪些由用户输入、引用或系统取得，及格式校验 |
| 处理与结果 | 正常步骤、输出、数据变更、可观察的成功结果和业务后置条件 |
| 异常 | 非法输入、无权限、资源缺失、业务条件不满足、重复或冲突等适用分支及结果 |
| 依赖与交接 | 调用哪个模块、由谁维护数据、交接前后条件及失败责任 |
| 验收 | 可检查的正常、异常及权限条件，关联用例位置 |
| 后续映射 | 对应原型、接口或内部调用、总体模块及详细设计；未形成时写待设计 |

数据名称、长度、允许值及统计口径复用数据分析和[共享登记](../data-analysis/shared-data-dictionary.md)。功能分析发现数据缺口时回到数据定义中确认，不在功能表里偷偷增加字段或改变状态。

## 权限与跨模块规则

按功能建立“角色—允许操作—数据范围—前置条件”的对应说明，沿用已确认的学生、工作人员、管理员范围，具体操作权限依据需求确认。后端核验与前端入口表现须一致，不能只写“已登录即可”。

自助取件沿用[ADR-005](../../management/decisions.md#adr-005跨文档分工统一与自助取件确认)：学生自助输入核验信息，系统校验并确认出库，工作人员不执行核验或确认。收件、取件、拒收、撤回及退件的交接由任奕阳与张海睿共同核对；寄件和统计衔接由沈翔宇与戴靖桓核对。规则出现冲突时先记录并协调确认。

## 评审与交接

汇总前检查全部REQ的确认范围是否有对应功能，功能是否有数据与流程依据，角色和异常分支是否遗漏，重复功能是否明确主责。各模块提供[追踪对应表](../../standards.md#统一编号与追踪)，与原型负责人核对每个功能项的原型图片。

至少一名其他成员评审，跨模块条件由受影响双方核对。记录待确认项及影响，确认后的功能作为原型、接口、系统设计和用例的输入。更新团队进度时区分本模块已编写、待评审及汇总结果，不将规范建立视为功能分析已完成。
