# 模块详细设计团队规范

## 依据与交付

开始前读取[团队进度](../../management/team.md)、[全过程规范](../../standards.md)、对应需求、数据与功能分析、原型、总体结构、[接口规范](../../api/README.md)、[OpenAPI](../../api/openapi.yaml)、[后端规范](../backend-design.md)及[数据库规范](../database-design.md)。涉及前端处理时同时执行[前端规范](../frontend-design.md)。

任奕阳、沈翔宇按团队计划主绘，各模块负责人提供并确认本模块处理逻辑。课程至少两个模块的程序流程图、N-S图或PAD图，导出图片汇入本目录DOCX，执行[CR-07](../../course-requirements.md)；其他模块进入实现前也要有明确逻辑和边界说明，不能把课程最低图数当作其余模块无需设计。

## 每个操作的设计内容

使用`LOG-<三位需求序号>-<两位流水号>`，关联功能、模块、数据项、原型及operationId；内部调用说明入口和调用者，不虚构HTTP端点。

| 内容 | 要求 |
| --- | --- |
| 输入输出 | 字段及类型引用契约和数据项；说明用户输入、系统取得及返回内容 |
| 权限与前置 | 身份、角色、资源范围、记录存在性及当前业务条件的校验顺序 |
| 正常路径 | 校验、读取、计算、修改、提交和响应步骤，明确由前端、Controller、Service或Repository承担 |
| 状态变化 | 引用已确认状态定义，说明原条件、触发、目标结果及不允许的分支 |
| 数据修改 | 读取与修改哪些业务事实，维护模块、字段映射及关联处理 |
| 事务与并发 | 共同成功或失败的范围、重复请求和并发冲突的处理方案及允许结果 |
| 失败路径 | 每个适用校验、调用或写入失败后的HTTP状态、错误码、数据结果及页面反馈 |
| 查询与统计 | 筛选、排序、分页或计算步骤，引用共享口径，说明时间边界和去重 |
| 验证 | 正常、异常、权限及涉及的并发或回滚用例，对应可观察的响应和存储结果 |

方法名、DTO、表列及状态值尚未设计时明确写待设计，不用任意名称填满图。影响实现的缺口确认后再进入对应编码，其他已确认部分可按依赖独立推进。

## 逻辑图与一致性

逻辑图使用一致图例和清晰的开始、结束、处理及判断节点，判断出口标明条件，失败分支必须指向确定结果。图中成功表示对应业务已满足成功条件，不能先返回成功再省略必要写入或事务提交。

事务边界及并发方案与数据库、后端设计共同核对。先查询再无条件写入不作为并发保证；重复提交、取件与拒收、撤回与退件开始等适用冲突须明确检查和修改如何保持一致。方案只选本次需要的机制，不机械加入所有锁或幂等组件。

前端格式校验与后端业务校验分别列明；调用方不能直接提交系统决定的最终结果绕过流程。接口字段、枚举、错误码和权限引用已确认契约，不在图中另造一套值。

## 评审与实现交接

按正常和失败场景逐步走读逻辑，检查每个输入能得到明确结果、失败后数据是否一致、跨模块调用由谁处理、页面反馈是否与响应一致。相关业务负责人及至少一名其他成员评审；涉及共享数据和事务时由受影响维护方参加。

交付逻辑说明、可编辑图、图片、课程DOCX、用例关联及未决项。实现后如处理逻辑改变，先按公共变更规则确认影响并同步设计与用例。走读结论只说明设计核对结果，不代表代码或事务已运行通过；实际进度及验证结果写入团队进度。
