# 数据库设计与开发规范

## 适用范围与依据

本文适用于校园快递收发系统的数据建模、表结构、字段、约束、索引、迁移、初始化数据及数据库相关修复，是项目工程约定。设计以已确认需求和数据分析为依据，不将数据分析表直接视作已评审表结构，也不凭规范新增业务实体或字段。

开始任务前必须阅读根目录[AGENTS.md](../../AGENTS.md)、[团队任务与进度](../management/team.md)、[团队协作规范](../collaboration.md)、[项目结构与分层](../architecture.md)、[开发环境](../development-environment.md)和本规范，同时读取本模块在`docs/requirements/data-analysis/`中的资料、已确认业务流程及现有数据库设计。涉及接口字段、事务或后端映射时，还必须阅读[接口规范](../api/README.md)、[OpenAPI](../api/openapi.yaml)和[后端设计与开发规范](backend-design.md)。

## 环境与文件位置

| 项目 | 规范 |
| --- | --- |
| 数据库 | MySQL8.4，镜像及启动参数以根目录[compose.yaml](../../compose.yaml)为准 |
| 字符集 | 沿用当前环境的`utf8mb4` |
| 排序规则 | 当前服务配置为`utf8mb4_0900_ai_ci`；字段比较要求与默认规则不一致时，在设计中说明并评审 |
| 时间约定 | 当前Compose数据库默认时区为`+08:00`，后端环境为`Asia/Shanghai`；字段类型、连接会话和接口转换须保持时间含义一致 |
| 数据连接 | 容器内使用`mysql:3306`；本机端口与账号按自己的环境配置，不提交真实口令 |
| 设计工作文件 | `database/design/` |
| 课程设计交付件 | `docs/design/database/`中的E-R图DOCX及按模板填写的表结构XLSX |
| 结构变更 | `database/migrations/` |
| 开发与测试种子数据 | `database/seeds/`；跨模块测试资料按现有目录放入`tests/fixtures/` |

字符集、排序规则和时区配置不等于字段语义已确定。涉及编码精确比较、唯一性或日期统计时，应检查实际库、表、列及连接会话的设置，不能仅根据服务默认值认定比较结果或时间转换正确。字符集与排序规则的关系见[MySQL8.4官方说明](https://dev.mysql.com/doc/refman/8.4/en/charset-mysql.html)。

## 设计流程与模块协作

1. 先明确REQ编号、实体含义、数据来源、使用角色和业务生命周期，再识别实体关系、字段、约束及访问方式。
2. 依据业务流程核对关系基数、可选关系、唯一范围和删除后的关联处理；跨模块共用数据由相关负责人共同确认，避免各模块重复维护含义相同的数据。
3. 由各模块负责人提交设计，沈翔宇按团队分工汇总数据库设计；公共结构变更由杨振煜协调受影响模块，沿用团队评审流程。
4. 设计先形成E-R图和表结构，再同步后端Entity、DTO映射及接口定义，确认后编写迁移。SQL中的名称、类型和约束必须能对应到设计资料。
5. 字段、业务枚举或删除规则缺乏依据时，列为待确认项并说明影响，不自行补齐为已确认需求。尚未确认的主键生成、持久化框架、迁移工具等方案，在选定后记录到[决策记录](../management/decisions.md)。

## 表与字段命名

表名和列名使用小写snake_case，使用明确、稳定的业务含义。同一概念在设计资料、SQL及Java映射中保持一致，Java和JSON名称按各自camelCase约定显式映射。

索引及约束名称应便于识别所属表、字段和用途，避免不同成员对相同规则重复创建对象。避免依赖名称大小写差异区分表或字段，也不使用模糊缩写掩盖业务含义。

每张表和每个字段均须有中文说明。表结构资料至少记录以下内容；课程交付时沿用教师模板，模板未覆盖的说明附在设计文档中。

| 层次 | 必须说明的内容 |
| --- | --- |
| 表 | 名称、用途、关联REQ、模块主责、实体关系及生命周期 |
| 字段 | 名称、含义、物理类型、长度或精度、是否可空、默认值及取值约束 |
| 主键 | 标识含义、物理类型、生成方式及被引用方式 |
| 关联 | 目标表与字段、关系基数、可空条件、一致性和删除处理 |
| 索引与约束 | 名称、涉及字段、顺序、唯一性范围及对应业务或查询依据 |
| 时间与状态 | 时间含义和精度、状态值来源、合法转换及维护方 |

## 类型、默认值与字段语义

1. 类型和长度来自数据分析中的实际范围与约束，不统一套用任意长度。手机号、单号、取件码等非计算标识按字符语义设计，保留可能存在的前导零，不因内容为数字而作为数值计算。
2. 数据库主键物理类型和生成策略单独评审。接口ID使用JSON字符串不意味着数据库必须使用字符主键，后端须保证两者映射准确。
3. 明确`NULL`、空字符串和缺省值的区别。`NOT NULL`和默认值应表达真实规则，不用空字符串、0或任意日期掩盖必填数据缺失。
4. 状态和字典值只来自已确认需求，说明允许值及由谁维护；选择数字、字符或关联字典等存储方式时写明依据，不能把不同模块各自定义的状态混用。
5. 时间字段注明表示日期还是具体时刻、由谁写入及如何转换到接口。选择`DATE`、`DATETIME`或`TIMESTAMP`等类型时，说明对应的时区和精度处理，不仅写“时间类型”。
6. 同一业务事实确定维护位置；需要冗余或历史快照时说明用途和一致性规则，不在多个表中无说明地重复维护可变数据。
7. 账号认证相关数据按已确认方案设计，不存储明文口令。删除标记、版本字段、创建更新时间等公共字段按实际设计需要确定，不默认给所有表增加一套字段。

## 关系、约束与索引

主键、非空和业务唯一性应在表结构中明确表达。唯一约束必须说明适用范围，并核对可空条件和字符比较规则；涉及被引用的数据时，说明停用、修改或删除对历史记录的影响，不能擅自设置级联删除。

实体关系须明确采用数据库外键还是由应用维护引用一致性，并写出理由和验证方式；未评审前不将任何一种方式当成所有表的默认结论。无论采用何种方式，都要防止无效引用并验证关联处理。

索引依据实际查询的筛选、关联、排序和唯一性需求设计，记录字段顺序及用途。避免重复索引和无查询依据的逐字段建索引；实现后通过代表性数据及执行计划核对效果，不能仅凭索引已建立宣称性能达标。

## 事务与业务一致性

与[后端规范](backend-design.md)共同确定事务边界，明确同一业务操作中哪些数据必须共同成功、失败后如何保持一致，以及并发操作允许产生什么结果。

取件、拒收、撤回及退件开始等相互影响的操作，必须保证已确认的业务条件在并发下仍成立。仅靠页面禁用或先查后无条件更新不能保证一致性；按实际方案使用条件更新、约束或锁等机制，并检查修改结果。存储引擎及事务方案须支持设计中要求的原子性和约束行为。

具体状态名称、唯一范围、重复提交处理及冲突响应由需求、数据与接口设计共同确认，不在数据库规范中另定义一套业务规则。

## 迁移与初始化数据

1. 结构变更统一进入`database/migrations/`，文件名使用`V<递增编号>__<说明>.sql`。新增编号前核对已有迁移并协调并行改动，保证顺序与编号不冲突。
2. 已合并并执行的迁移不得改写；后续修正新增迁移。迁移工具在应用初始化时统一确定，不能因为文件采用该命名就宣称已接入某种工具。
3. 每次变更说明原因、关联需求、受影响表及调用方、已有数据处理、执行顺序和失败后的恢复方案。删除字段、收紧约束或改变类型前核查存量数据及后端兼容性。
4. 不将MySQL结构变更的恢复等同于普通业务事务回滚；多种DDL语句会隐式提交。结构迁移要单独考虑备份、恢复或后续修复步骤，依据见[MySQL8.4隐式提交说明](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)。
5. 种子数据仅使用可公开的合成数据，说明用途、依赖及重复执行策略。开发测试数据和必需的基础字典分别说明，不把样例记录当成真实业务证据。
6. 不依赖成员手工修改数据库作为唯一变更交付；SQL、设计和应用映射同步维护。不得通过删除共享数据或重置卷来掩盖迁移失败。

## 验证与交付

在可用的MySQL环境中，按本次改动验证迁移执行、实际表结构、约束及相关数据操作。新增建库路径和已有版本升级路径有影响时分别验证；对本次涉及的非空、唯一、关联、时间和编码边界提供对应结果，事务或并发变更验证失败及冲突后的数据一致性。

记录数据库版本、起始结构版本、迁移文件、实际命令、预期与实际结果及证据。缺少环境或应用时标明未执行及原因；SQL文本检查、Compose配置解析或数据库健康检查不能替代迁移和业务验证。

课程交付仍按[课程交付要求](../course-requirements.md)提供E-R图DOCX和表结构XLSX，Markdown规范不能替代正式材料。交付前核对需求、数据分析、E-R图、表结构、迁移、Entity及接口映射的一致性，并在`docs/management/team.md`更新实际完成情况与遗留事项。本文建立数据库工程规则，不代表表结构、迁移工具及运行结果已经确认。
