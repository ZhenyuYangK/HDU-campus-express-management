# 系统总体设计团队规范

## 依据与范围

开始前读取[团队进度](../../management/team.md)、[全过程规范](../../standards.md)、[项目结构与分层](../../architecture.md)、[接口规范](../../api/README.md)、[OpenAPI](../../api/openapi.yaml)及本次模块的需求、数据、功能和原型。涉及前后端、数据库及运行配置的部分，分别读取对应设计规范和[开发环境](../../development-environment.md)。

总体设计明确系统由哪些模块组成、各模块负责什么、如何协作以及公共能力如何复用。采用已确认的Spring Boot+Vue3+MySQL及现有分层，不因绘制结构图增加未经确认的服务、平台或业务范围。

## 模块说明与结构图

每个模块使用`MOD-<三位需求序号>-<两位流水号>`，说明对应REQ和功能、职责边界、维护的数据、调用方、依赖方、输入输出及异常交接。模块主责沿用[团队分工](../../management/team.md)，不能因某人负责材料汇总就转移业务维护责任。

结构图必须配套图例，分别表达模块包含关系和调用或数据依赖，箭头方向一致；需要时拆成多张图，不把功能层级、部署结构和调用链混在同一套无说明的连线中。课程结构图导出图片并汇入DOCX，保存于本目录，执行[CR-05](../../course-requirements.md)。可编辑源文件与导出图一起保留。

## 必须明确的协作边界

| 范围 | 设计内容 |
| --- | --- |
| 前端 | 角色入口、页面与模块关系、公共布局和组件、统一请求及类型维护位置 |
| 后端 | Controller、Service、Repository职责，业务入口及公共权限、响应、异常等能力 |
| 数据 | 哪个模块维护业务事实、哪些模块读取，共享数据引用及历史数据处理原则 |
| 跨模块调用 | 输入输出、前置与后置条件、失败返回和事务归属，不为每个内部调用机械增加HTTP接口 |
| 外部HTTP接口 | 关联功能与OpenAPI的operationId，权限及数据范围由契约确认 |
| 运行结构 | 前端、后端、数据库的运行关系与配置来源，沿用现有环境，区分已有与待建能力 |
| 公共依赖 | 谁负责提供、使用方需要什么、确认状态及缺失时影响的后续任务 |

共用数据由维护模块提供统一业务入口，其他模块不能自行绕过规则改表。既有Controller→Service→Repository分层与接口DTO、持久化实体分离规则继续生效。结构设计明确依赖方向，避免循环调用和同一数据由多方无说明地修改。

未确认的认证、持久化、迁移及其他公共技术选择列为待决事项，由杨振煜组织受影响成员评审并记录到决策记录；不在模块设计里各选一套。

## 验收与交接

杨振煜组织各模块核对功能是否有归属、共享能力是否重复、依赖是否清楚、收件到取件以及其他跨模块交接能否按设计走通。设计中的HTTP接口转入接口登记，数据关系转入数据库设计，具体处理步骤转入详细设计。

交付保留模块说明、结构图及功能对应关系、公共依赖与未决项、评审记录和课程DOCX。图文与现有项目结构一致，导出图片可读；更新团队进度，区分总体设计评审、接口确认和实际实现状态。
