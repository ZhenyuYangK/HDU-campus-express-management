# 后端设计与开发规范

## 适用范围与依据

本文适用于校园快递收发系统的后端设计、应用初始化、接口实现、业务逻辑、数据访问及相关修复，是项目工程约定。业务范围、角色与模块归属沿用已确认资料；本文不新增业务需求、端点、状态枚举或数据库表，也不代表后端已经实现。

开始任务前必须阅读根目录[AGENTS.md](../../AGENTS.md)、[团队任务与进度](../management/team.md)、[团队协作规范](../collaboration.md)、[接口规范](../api/README.md)、[OpenAPI](../api/openapi.yaml)、[项目结构与分层](../architecture.md)和本规范；同时读取本模块已确认的需求、业务流程、功能分析及详细设计。涉及持久化、事务或数据结构时，还必须阅读[数据库设计与开发规范](database-design.md)及对应数据分析、表结构资料。

## 技术与配置

| 项目 | 规范 |
| --- | --- |
| 技术栈 | Spring Boot、Java21、Maven；环境依据见[开发环境](../development-environment.md) |
| 根包 | `cn.edu.hdu.express` |
| 源码与资源 | Java代码放`backend/src/main/java/`，应用配置放`backend/src/main/resources/` |
| 版本管理 | 初始化时在`pom.xml`固定Spring Boot及依赖版本，不直接使用未确认版本 |
| 持久化 | 在应用初始化时统一确定框架，记录到[决策记录](../management/decisions.md)，各模块沿用同一方案 |
| 认证 | 三类角色已确认，具体认证方案和权限映射须设计确认；不提前选定JWT、Session等方案 |
| 配置来源 | 使用环境变量及已提交的配置模板；数据库口令不写入源码、构建文件或日志 |

容器内后端使用`mysql:3306`访问数据库，通过现有`SPRING_DATASOURCE_*`变量接入。宿主机调试地址按实际环境配置，不将容器内`localhost`当作数据库服务。端口、跨域及代理设置与根目录Compose和开发环境文档同步。

## 分层与命名

按现有Controller→Service→Repository结构组织实现，不为单个模块另建一套公共协议或数据访问框架。

| 目录或类型 | 职责 | 约束 |
| --- | --- | --- |
| `controller/` | 接收HTTP请求、绑定参数、执行参数校验并调用Service | 不直接访问Repository，不在入口堆放业务流程 |
| `service/` | 业务条件、资源访问权限、状态转换、事务和跨数据操作协调 | 业务入口统一执行规则，不依赖前端先行校验 |
| `repository/` | 持久化、条件查询及受约束的数据修改 | 不决定HTTP状态，不自行改变业务规则 |
| `dto/request/` | 对外请求字段和参数约束 | 只接收契约允许调用方设置的字段 |
| `dto/response/` | 对外响应字段及序列化映射 | 不直接返回Entity或内部敏感字段 |
| `entity/` | 数据库实体映射 | 与表结构一致，和接口DTO分别维护 |
| `config/` | 框架及环境配置 | 公共配置变更先协调受影响成员 |
| `common/exception/`、`common/response/`、`common/validation/` | 统一异常、响应及公共校验 | 各模块复用，不复制不同版本 |

Java类名使用PascalCase，方法和变量使用camelCase；文件使用UTF-8、LF，Java缩进遵循根目录`.editorconfig`的4空格。类名、方法名表达业务含义；公共抽取以实际复用为依据，不预先增加无需求依据的层次或组件。

## 接口设计与参数校验

1. 每个业务接口先关联REQ编号，明确调用角色、数据访问范围、输入输出、正常及异常条件、验收用例，再登记OpenAPI及接口说明；评审确认后进入实现。
2. 基础路径、方法、字段、必填与可空、HTTP状态、错误码、分页及时间格式，以接口规范和OpenAPI为准。新增或变更时同步两份资料及调用方，不能仅在Java代码里修改协议。
3. 请求DTO执行格式、长度、范围等参数校验；Service核对资源归属、记录存在性和当前业务条件。两类校验分别覆盖，前端隐藏按钮或限制输入不能替代后端校验。
4. 调用方不能通过请求覆盖系统决定的角色、资源归属或处理结果。哪些字段可修改必须在契约中列明，不将请求对象直接整体复制到持久化实体。
5. ID、单号、手机号等标识在JSON中使用字符串；数据库主键的物理类型另按数据库设计确定。日期时间按RFC3339输出时区信息，纯日期不混入时间。
6. 成功和失败响应使用公共结构；`data`为对象或`null`，列表放入`data.items`。分页沿用`page`从1开始、`size`默认20且范围1～100，非法参数返回400；排序字段采用明确映射，不拼接调用方传入的SQL片段。
7. 按公共契约校验或生成`X-Request-Id`，在响应头和响应体返回同一值，并用于关联日志。异常统一转换为已登记的HTTP状态及错误码，不把所有失败包装成HTTP200。

## 权限与业务规则

学生、工作人员、管理员的具体操作权限在需求和接口评审时确定。后端必须同时核验身份、角色及目标资源的访问范围，不能仅凭调用方提交的用户ID判断操作人身份。

已确认的自助取件规则以[ADR-005](../management/decisions.md#adr-005跨文档分工统一与自助取件确认)和[接口规范](../api/README.md)为依据：学生提交取件码和收件手机号后四位，由系统结合当前业务条件核验并确认出库；工作人员不执行取件核验或确认。核验失败、重复取件、拒收暂停、撤回恢复及退件开始后的限制必须在后端执行。具体状态名和字段名仍由需求、数据及接口设计统一确定。

跨收件、自助取件、拒收与退件的条件由相关模块共同核对，其他模块按各自已确认规则设计。不能因前端暂未提供某个入口，就省略后端对应的权限或状态约束。

## 事务、并发与数据访问

1. 以一个完整业务操作确定Service事务边界，列出需要共同成功或失败的数据修改。事务配置与异常处理共同检查，不能吞掉异常后返回成功，造成部分写入。
2. 对重复提交或并发修改，设计时写明允许结果、冲突判断和数据库保证方式；方案按实际需求选择条件更新、约束或锁等机制，不默认引入所有机制。
3. 先查询再无条件写入不能作为并发保证。涉及取件和拒收、撤回和退件开始等相互影响的操作，校验与修改必须能在并发下保持已确认条件，修改结果须检查后再返回成功。
4. Repository使用参数绑定或框架提供的安全参数机制。查询条件、排序和分页范围明确；学生个人查询必须带上后端确定的访问范围。
5. 列表返回字段和关联查询按接口需要确定，避免无界读取；统计的筛选范围、时间边界和计算口径必须有对应需求依据。
6. 事务、约束、索引和数据类型与数据库规范共同设计。持久化异常通过统一异常处理映射到接口错误，不向调用方输出SQL、表结构细节或连接信息。

## 日志与异常

记录定位问题所需的请求标识、操作结果和异常上下文；不输出口令、认证凭据、完整取件核验信息或无关个人信息。预期业务失败按契约返回可理解的信息，未预期异常按公共错误协议处理，必要堆栈仅保留在受控服务端日志中。

公共响应、异常映射和权限组件由公共变更负责人协调，各模块不得为绕过约定而新建私有替代实现。

## 验证与交付

后端初始化前不在占位目录执行应用测试并宣称通过。应用建立后，按变更范围执行构建、相关模块测试及必要的数据库或接口集成验证；`mvn test`等命令的实际执行位置、环境、结果和证据写入交付记录。

业务验证至少覆盖本次改动涉及的正常流程、非法输入、访问越权和业务条件失败；涉及事务或并发时，再验证部分失败、重复请求或并发冲突下的数据结果。公共协议变化核对响应结构、HTTP状态和调用方兼容性，不能用编译成功代替这些验证。

交付前核对需求、OpenAPI、DTO、实体映射及相关数据设计是否一致，执行[团队协作规范](../collaboration.md)的评审要求，并在`docs/management/team.md`记录完成情况、真实验证结果和未完成事项。本文建立后端工程规则；具体框架选型、接口确认和业务实现按对应任务继续推进。
